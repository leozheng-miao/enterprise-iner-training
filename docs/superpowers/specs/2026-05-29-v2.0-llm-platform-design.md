# v2.0「LLM 平台化基建」设计规范

> **基线**：v1.0.0 (`8907a85`)
> **里程碑**：v2.0（v2.0 → v2.1 → v2.2 三段拆分中的第一段）
> **范围**：#3 OpenTelemetry 接入 + #4 Spring AI Advisors 替换 PromptLoader + #5 多 LLM Provider
> **不在范围**：用户自定义 Workflow（v2.1）、知识入库二期（v2.1）、付费功能（v2.2）
> **预计工程量**：~17 人天 / 2-3 周

---

## §1 决策清单（与用户对齐的所有取舍）

| 项 | 决定 |
|---|---|
| 范围 | #3 OTel + #4 Advisors + #5 多模型，不含自定义 Workflow / 知识入库 / 付费 |
| Provider | DashScope（保留）+ vLLM（保留）+ **OpenAI 官方（新）** + **DeepSeek 官方（新）** |
| 路由维度 | Agent 角色 + Prompt 版本，**两者解耦**，独立灰度 |
| 路由存储 | 改 `prompt_template` + 新增 `agent_model_routing` + `routing_change_log` |
| Embedding | 单 Provider（DashScope），接口预留，运行时禁切（切 model 需 reindex） |
| Rerank | 多 Provider 接口预留，先单 DashScope |
| Resilience | 同 Provider 候选 fallback（默认开）+ 跨 Provider fallback（默认关、Admin 可开）+ Resilience4j retry/CB + **告警系统** |
| Advisor 链 | PromptResolution / Trace / TokenUsage / Resilience **四件套**；不要 QA/Memory Advisor |
| 上下文模型 | 新增 `WorkflowContext` / `AgentContext`，5 Agent 间传递任务上下文；RAG 保持自研 |
| OTel | traces + metrics 都做；自研 `workflow_node_run` 表**双写保留** |
| 基础设施 | docker-compose 加 **Jaeger / Prometheus / Grafana / OTel Collector** |

**用户驳回 / 修正的关键点（避免再次踩坑）**：
1. Prompt 与 Model 必须**解耦**——直觉胜过"一行省事"。Prompt 工程师和模型选型是两件事。
2. RAG **保留自研** Hybrid + RRF + Rerank + Citation，不收进 Spring AI 的 QuestionAnswerAdvisor——这是简历亮点，藏进框架反而埋没。
3. **不要 ChatMemory**，改用 `WorkflowContext` 跨 Agent 传递上下文——这是 5 Agent 协作架构的正确抽象，比"多轮记忆"贴合场景。
4. 告警是一等公民，不是事后追加——v2.0 引入 `alert_event` 表 + Webhook + Admin SSE 推送。

## §3 LLMGateway 抽象层（#5 多模型核心）

### 3.1 接口分层

```java
// 顶层门面
public interface LLMGateway {
    ChatResponse chat(AgentRole role, ChatRequest req, WorkflowContext ctx);
    Flux<ChatResponse> stream(AgentRole role, ChatRequest req, WorkflowContext ctx);
    List<Embedding> embed(EmbedRequest req);
    List<RerankItem> rerank(RerankRequest req);
}

// Provider 维度的服务接口
public interface ChatService {
    Provider provider();             // OPENAI / DEEPSEEK / DASHSCOPE / VLLM
    boolean supports(String model);
    ChatResponse call(ChatRequest req, AdvisorContext adv);
    Flux<ChatResponse> stream(ChatRequest req, AdvisorContext adv);
}

// 路由
public interface ModelRouter {
    ResolvedRoute resolve(AgentRole role, Long tenantId);
}
// ResolvedRoute = { provider, primaryModel, sameProviderFallbacks, crossProviderFallbacks, crossEnabled, promptVersion }
```

### 3.2 4 个 Provider 实现的复用策略

| Provider | 实现方式 | 复用 |
|---|---|---|
| **DashScope** | 走 OpenAI 兼容 endpoint | Spring AI `OpenAiChatModel`，base-url 改为 dashscope |
| **OpenAI 官方** | Spring AI `OpenAiChatModel` 原生 | — |
| **DeepSeek 官方** | OpenAI 兼容 endpoint | Spring AI `OpenAiChatModel`，base-url 改为 deepseek |
| **vLLM** | OpenAI 兼容 endpoint | Spring AI `OpenAiChatModel`，base-url 指 vLLM |

四者都走 OpenAI 协议，**底层 ChatModel 类型相同，只是 4 个不同的 Bean 实例**。每个 Bean 配独立 `api-key + base-url + default-model`，Spring `@Qualifier` 区分注入。未来要接 Anthropic 时再独立写 `AnthropicChatServiceImpl`，那时才真正考验抽象。

### 3.3 ModelRouter 决策流

```
ModelRouter.resolve(agentRole='Planner', tenantId=1)
  ├─ 查 agent_model_routing where agent='Planner' and active=1 and tenant_id in (0, 1)
  │   优先 tenant_id=1，回落 tenant_id=0
  │   命中：provider=OPENAI, primary=gpt-4o,
  │        sameProviderFallbacks=['gpt-4o-mini'],
  │        crossProviderFallbacks=[{provider:DASHSCOPE, model:qwen-max}],
  │        crossEnabled=false
  ├─ 查 prompt_template where agent_role='Planner' and active=1 and tenant_id in (0, 1)
  │   命中：version='v3', text='...{{topic}}...'
  └─ 返回 ResolvedRoute { provider, primary, fallbacks..., promptVersion=v3 }
```

**缓存策略**：路由结果 in-memory cache 5s（防瞬时高并发 DB 压力，灰度切换生效延迟可接受）。

## §5 Advisor 链：4 件套各自的职责与边界

**执行顺序**（注册顺序 = 执行顺序）：

```
ChatClient.prompt()
   ▼
[1] PromptResolutionAdvisor   ← before: 装载 prompt
   ▼
[2] ResilienceAdvisor         ← around: retry + CB + fallback（最外圈包真正的 HTTP）
   ▼
[3] TraceAdvisor              ← around: openSpan / closeSpan + 写 workflow_node_run
   ▼
[4] TokenUsageAdvisor         ← after: 从 ChatResponse.metadata 读 tokens
   ▼
真正的 HTTP 调用（Spring AI OpenAiChatModel）
```

### 5.1 PromptResolutionAdvisor

```java
@Component
public class PromptResolutionAdvisor implements CallAroundAdvisor {

    public AdvisedResponse aroundCall(AdvisedRequest req, CallAroundAdvisorChain chain) {
        AgentRole role = req.adviseContext().get("agentRole", AgentRole.class);
        Long tenantId = req.adviseContext().get("tenantId", Long.class);
        Map<String, Object> vars = req.adviseContext().get("vars", Map.class);

        PromptTemplateVO tpl = promptService.findActive(role, tenantId);
        String filled = TemplateRenderer.render(tpl.getTextTemplate(), vars);

        AdvisedRequest updated = req.updated()
            .userText(filled)
            .adviseContext("promptVersion", tpl.getVersion())
            .build();

        return chain.nextAroundCall(updated);
    }

    @Override public String getName() { return "PromptResolution"; }
    @Override public int getOrder() { return 100; }
}
```

**AdvisorContext 必须带的 key**：`agentRole, tenantId, vars, workflowContext, taskId, nodeName, route`。这些由 LLMGateway 在调用前填充。

### 5.2 ResilienceAdvisor

```java
public AdvisedResponse aroundCall(AdvisedRequest req, CallAroundAdvisorChain chain) {
    ResolvedRoute route = req.adviseContext().get("route", ResolvedRoute.class);
    String cbName = "llm." + route.provider() + "." + route.primaryModel();

    Supplier<AdvisedResponse> primary = () -> chain.nextAroundCall(req);
    Supplier<AdvisedResponse> decorated = CircuitBreaker
        .decorateSupplier(cbRegistry.circuitBreaker(cbName), primary);
    decorated = Retry.decorateSupplier(retryRegistry.retry(cbName), decorated);

    try {
        return decorated.get();
    } catch (Exception e) {
        // 1) 同 Provider 内候选 fallback
        for (String alt : route.sameProviderFallbacks()) {
            try { return invokeWithAlternateModel(req, route.provider(), alt, chain); }
            catch (Exception ex) { /* try next */ }
        }
        // 2) 跨 Provider fallback（仅 cross_enabled = true）
        if (route.crossEnabled()) {
            for (ProviderModel pm : route.crossProviderFallbacks()) {
                try {
                    alertService.warn("CROSS_FALLBACK_TRIGGERED",
                        Map.of("from", route.primaryModel(), "to", pm.toString()));
                    return invokeWithAlternateRoute(req, pm, chain);
                } catch (Exception ex) { /* try next */ }
            }
        }
        // 3) 全部失败：CRITICAL 告警 + 抛
        alertService.critical("LLM_ALL_FALLBACK_EXHAUSTED",
            Map.of("agent", req.adviseContext().get("agentRole"), "route", route));
        throw new BusinessException(ErrorCode.LLM_UNAVAILABLE);
    }
}
```

**⚠️ 重要陷阱**：fallback 切到不同 model 时实际是「在 ResilienceAdvisor 内部直接调另一个 ChatService.call(...)」**绕过下游 advisor**——TraceAdvisor / TokenUsageAdvisor 在 fallback 路径上需手动补埋点。`invokeWithAlternateModel / invokeWithAlternateRoute` 实现必须包含 span+token 补埋。单测必须覆盖此场景。

### 5.3 TraceAdvisor

```java
public AdvisedResponse aroundCall(AdvisedRequest req, CallAroundAdvisorChain chain) {
    String taskId   = req.adviseContext().get("taskId", String.class);
    String nodeName = req.adviseContext().get("nodeName", String.class);
    ResolvedRoute route = req.adviseContext().get("route", ResolvedRoute.class);

    Span span = tracer.spanBuilder("llm." + nodeName)
        .setAttribute("llm.provider", route.provider().name())
        .setAttribute("llm.model", route.primaryModel())
        .setAttribute("llm.prompt_version", req.adviseContext().get("promptVersion", String.class))
        .setAttribute("workflow.task_id", taskId)
        .startSpan();

    long t0 = System.nanoTime();
    try (Scope ignore = span.makeCurrent()) {
        AdvisedResponse resp = chain.nextAroundCall(req);
        long latencyMs = (System.nanoTime() - t0) / 1_000_000;

        recorder.record(WorkflowNodeRun.builder()
            .taskId(taskId).nodeName(nodeName)
            .traceId(span.getSpanContext().getTraceId())
            .spanId(span.getSpanContext().getSpanId())
            .routingSnapshot(route.toJson())
            .latencyMs(latencyMs).status("OK").build());

        span.setStatus(StatusCode.OK);
        return resp;
    } catch (Exception e) {
        span.recordException(e);
        span.setStatus(StatusCode.ERROR, e.getMessage());
        recorder.recordFailure(taskId, nodeName, e);
        throw e;
    } finally {
        span.end();
    }
}
```

### 5.4 TokenUsageAdvisor

```java
public AdvisedResponse aroundCall(AdvisedRequest req, CallAroundAdvisorChain chain) {
    AdvisedResponse resp = chain.nextAroundCall(req);

    Usage usage = resp.response().getMetadata().getUsage();
    ResolvedRoute route = req.adviseContext().get("route", ResolvedRoute.class);

    long cost = ModelPricing.costInCents(route.provider(), route.primaryModel(),
        usage.getPromptTokens(), usage.getCompletionTokens());

    WorkflowContext ctx = req.adviseContext().get("workflowContext", WorkflowContext.class);
    ctx.addTokens(usage.getPromptTokens(), usage.getCompletionTokens(), cost);

    meterRegistry.counter("llm.tokens.input",
        "provider", route.provider().name(), "model", route.primaryModel())
        .increment(usage.getPromptTokens());
    meterRegistry.counter("llm.tokens.output", ...).increment(usage.getCompletionTokens());
    meterRegistry.counter("llm.cost.cents", ...).increment(cost);

    return resp;
}
```

### 5.5 改造前后对比（Agent 角度）

**v1.0.0 Researcher 写法**：
```java
String prompt = promptLoader.load("researcher", Map.of("topic", topic));
ChatClient client = ChatClient.create(chatModel);
String result = client.prompt(prompt).call().content();
recorder.record(...);          // 手动埋
tokenAccumulator.add(...);     // 手动埋
```

**v2.0 Researcher 写法**：
```java
ChatResponse resp = llmGateway.chat(AgentRole.RESEARCHER,
    ChatRequest.builder().vars(Map.of("topic", topic)).build(),
    workflowContext);
String result = resp.content();
// 不用手动 record / 不用算 token / 不用关心用哪个 model
```

散在 `agent/role/*` 7 个 Agent 里的 LLM 调用样板代码（约 200+ 行）→ 收成统一一行 `llmGateway.chat(...)`，所有切面统一在 Advisor 链。

### 6.1 OTel 接入路径

### 6.4 告警系统设计

| 严重度 | 触发条件 |
|---|---|
| INFO | 单次 retry 成功（仅写 `alert_event`，不通知） |
| WARN | 触发同/跨 Provider fallback 成功 |
| CRITICAL | 所有 fallback 耗尽抛错 / CB open / 5 分钟内同一 model 失败 ≥10 次 |

**通道（v2.0 范围）**：

| 通道 | 状态 |
|---|---|
| DB 落库 (`alert_event`) | 必做，全部严重度 |
| 前端 Admin 红点 | 必做（TopBar 铃铛 + SSE 实时推） |
| Webhook（飞书/钉钉/Slack 通用） | 必做，**仅 CRITICAL** 触发 |
| Email / 短信 | 不做，留 v2.2 |

```java
public interface AlertService {
    void info(String source, Map<String, Object> payload);
    void warn(String source, Map<String, Object> payload);
    void critical(String source, Map<String, Object> payload);
}
```

`DefaultAlertService` 三件事：(1) 同步写 `alert_event`；(2) CRITICAL 异步发 Webhook（@Async + retry 3 次）；(3) SSE 广播 `alert.created` 给已连接的 Admin 流。

### 6.5 OTel 与自研 Trace 互补关系

```
LLM 调用                              OTel span 链
   ▼ TraceAdvisor                          ▼
   ├──→ Recorder.record() ──→ workflow_node_run (MySQL)
   │                          ├─ trace_id ←┐
   │                          ├─ span_id  ←┤ 来自 OTel Context
   │                          └─ ...        │
   └──→ Span emit ──────────────→ Jaeger ──┘ 同一 trace_id
```

两套数据**不竞争，只互补**：
- 自研表：聚合查询（AdminStats 同比 / P95）、租户隔离、Token 成本
- Jaeger：详细 trace 树、跨服务 / 跨 MQ 调用链、调试一次具体失败

## §7 WorkflowContext / AgentContext + 5 Agent 改造

### 7.1 上下文模型

```java
public class WorkflowContext {
    private final String taskId;
    private final Long tenantId;
    private final String traceId;
    private final String workflowName;
    private final String topic;

    private PlanResult plan;                                       // Planner 产出
    private final List<SubtaskResult> subtasks = new ArrayList<>(); // Researcher × N
    private OutlineResult outline;                                 // Analyst 产出
    private final List<SectionDraft> sections = new ArrayList<>(); // Writer × M
    private CriticResult critic;                                   // Critic 产出
    private final List<Citation> citations = new ArrayList<>();

    private final TokenAccumulator tokens = new TokenAccumulator();
    private final List<String> spanIds = new ArrayList<>();

    private final Map<String, Object> extra = new ConcurrentHashMap<>();

    public byte[] toMqPayload();
    public static WorkflowContext from(byte[] payload);
}

public class AgentContext {
    private final WorkflowContext parent;
    private final AgentRole role;
    private final String nodeName;
    private final Map<String, Object> inputVars;

    public ChatRequest toChatRequest();
}
```

### 7.2 上下文流转

```
Planner → 写 ctx.plan → 序列化进 irp-research-subtask payload
     ▼
Researcher Worker × N（每 worker 反序列化拿 ctx 副本）
  - 执行 hybrid_search
  - 写 subtaskResult 进副本
  - 提交结果 + ctx delta 进 JoinTracker
     ▼ JoinTracker.allDone() → merge N 份副本 → 完整 ctx
Analyst → Writer × M（fanout/fanin 同 Researcher） → Critic
```

### 7.3 MQ payload 大小处理

| 字段 | 处理 |
|---|---|
| `taskId, tenantId, traceId, topic, plan, outline, critic` | 直接进 payload（小） |
| `subtasks / sections / references / citations` | **大字段卸载**：>64KB 时写已有 DB 表（`report_section/workflow_subtask`）+ payload 只存 ID。读时 lazy load |
| `extra` | 直接进 payload，限 16KB |

封装 `WorkflowContextSerializer`，监控 `mq.payload.size.bytes` metric。

### 7.4 5 Agent 改造对照

| Agent | v1.0.0 | v2.0 |
|---|---|---|
| Planner | `promptLoader.load + chatClient.prompt(...)` + 手动 record | `llmGateway.chat(PLANNER, ChatRequest.with(topic), ctx)`；结果写 `ctx.plan` |
| Researcher | tool 调用 + chat + 手动管 ctx | tool 调用保留（HybridSearchTool 不动）；chat 改 gateway；结果写 `ctx.subtasks` |
| Analyst | 同 Planner | 同 Planner（读 `ctx.subtasks`，写 `ctx.outline`） |
| Writer | 章节级 chat | 派生 AgentContext 按 section 调 gateway |
| Critic | chat + 回环判断 | 同上，回环逻辑用 `workflow_loop_state` 不动 |
| QueryRewriter | 独立 `QueryRewriterClient` | 收编为 `llmGateway.chat(QUERY_REWRITER, ...)`，路由表配 vLLM 主 + DashScope 兜底 |
| Judge | `ReportJudgeService` 手写多模型 | 收编为 `llmGateway.chat(JUDGE, ...)`；`judge-model-candidates` 配置废弃 |

## §10 风险与缓解

| 风险 | 概率 | 缓解 |
|---|---|---|
| Spring AI 1.0.0 Advisor API 在 1.0.x 间 break | 中 | Advisor 实现包薄壳；锁版本 1.0.0 |
| 跨 Provider fallback 引产出质量回归 | 中 | 默认关闭；WARN 告警让运营感知；保留快速关闭开关 |
| MQ payload 超 RocketMQ 默认 4MB 限制 | 中 | WorkflowContextSerializer 卸载；监控 `mq.payload.size.bytes` |
| OTel 全采样 prod 时存储/带宽爆炸 | 低 | sampler 默认 1.0 仅 dev；prod yml 用 0.1 + 关键 span force-on |
| 4 个 Provider api key 泄漏 | 高（人为） | `.env` gitignore；启动校验 key 格式不打日志；新增前置 sanity check |
| Resilience4j retry 跟 OTel context 串台（child span 错挂） | 低 | 已知 Spring AI 1.0 + r4j 集成有坑；单测覆盖此场景 |
| 双写时序错位（advisor 抛异常后 finally 才 end span） | 低 | 单测覆盖 + spec 写明 try/finally 模板（见 §5.3） |
