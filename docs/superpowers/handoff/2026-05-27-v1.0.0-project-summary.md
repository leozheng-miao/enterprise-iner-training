## 0. 一句话项目

输入研究主题 → **5 个 Agent 协作**（Planner / Researcher × N / Analyst / Writer × M / Critic）→ **流式产出带引用的 Markdown 研报**。

不止 demo，平台能力一应俱全：**Prompt 灰度 / Trace 观测 / Token 成本看板 / 多租户 / LoRA 微调 / LLM-as-Judge / Workflow 热更新审计 / 子服务健康监测**。

定位：**1-3 年 Java 转 AI Agent 后端**求职项目，覆盖 China AI Agent 2026 JD 的全部关键词。

## 4. 5 Agent 协作流程（核心叙事）

```
[用户提交主题] POST /api/report/start
        │
        ▼  RocketMQ: irp-task-created
┌──────────────────┐
│ TaskOrchestrator │   ↓ Planner LLM 产出 N 个子主题
│  Planner (LLM)   │
└──────────────────┘
        │ fanout N 条子主题  → MQ: irp-research-subtask
        ▼
┌────────────────────────┐
│  Researcher Worker × N │  hybrid_search Tool (RAG)
└────────────────────────┘
        │ N 条全部完成（JoinTracker）→ MQ: irp-research-done
        ▼
┌────────────────────────┐
│  Analyst (LLM)         │  推理 + 章节大纲
└────────────────────────┘
        │ fanout M 个章节 → MQ: irp-section-task
        ▼
┌────────────────────────┐
│  Writer Worker × M     │  每章节独立生成 Markdown
└────────────────────────┘
        │ join all → MQ: irp-section-done
        ▼
┌────────────────────────┐
│  Critic（≤1 loop）      │  事实/逻辑自检；不通过则触发 Writer 二刷
└────────────────────────┘
        │ 全程 workflow_node_run 落库 + Redis Pub/Sub
        ▼
   SSE 流到前端（7 种事件类型）
```

**为什么这么设计：**
1. **可观测** — `workflow_node_run` 每节点一行：input/output/tokens/latency/status，天然 Trace。
2. **可重试** — 单节点失败只重试自己（RocketMQ 16 次 + 死信）。
3. **可水平扩展** — Researcher/Writer Worker 可多实例并行消费同一 topic。
4. **可暂停恢复** — 状态全在 DB，任意时刻崩溃重启不丢任务。
5. **跨实例 SSE** — Redis Pub/Sub 广播事件，前端订阅哪个实例都拿得到。

| `tool_registry` | Tool SPI 注册表 | `schema-phase2.sql` |
| `prompt_template` | Prompt 版本管理（含 `@active` 列） | `schema-phase4.sql` |
| `report_eval_run` | LLM-as-Judge 评分记录 | `schema-phase6.sql` |
| `knowledge_doc` | 文档元信息 | `schema-rag.sql` |
| `knowledge_chunk` | chunk 索引 + ES 写入触发 | `schema-rag.sql` |
| `rag_eval_query` | RAG 离线评估 query set | `schema-rag.sql` |
| **`workflow_load_log`** | **Workflow 加载审计（F4 新增）** | **`schema-phase7.sql`** |
| (pgvector) `knowledge_chunk_vec` | 向量表（独立 PG 实例） | `pgvector-init.sql` |

**所有业务表的公共字段**（来自 `BaseEntity`）：
- `id BIGINT AUTO_INCREMENT`
- `create_time DATETIME` (DB now() 填充)
- `update_time DATETIME` (DB now() ON UPDATE 填充)
- `is_deleted TINYINT DEFAULT 0` (逻辑删除)

**`workflow_load_log` 例外**：纯日志，不继承 BaseEntity，只有 `id` + `ts` (epoch millis)。

## 11. 关键约定 / 易踩坑（必读）

### 11.1 字段命名规约（F3 测试期踩过 3 次）

| 规则 | 反例 | 正例 |
|---|---|---|
| Lombok `boolean` 字段 Jackson 序列化丢 `is` 前缀 | 前端写 `isActive` | 前端写 `active`（与 `PromptTemplateVO`）； `ActiveWorkflowVO.cached` 同理 |
| 时间字段后端不统一 | 混用 `createTime` 和 `createdAt` | F4 新增字段一律 `xxxAt` (epoch millis Long)；历史字段不动 |
| `TaskBriefVO` 没有 `startedAt` / `finishedAt` | 前端直接读取 | 后端只给 `latencyMs` + `createdAt` |
| `PlatformOverviewVO` 没有 `successRate` / `p95LatencyMs`（旧版） | 直接用 | F4 后才有 `p95TaskLatencyMs`；旧字段是 `taskSuccessRate` |

### 11.2 P95 阈值

`overview()` 的 `p95TaskLatencyMs` **窗口内 DONE 任务 < 20 时返回 `null`**。前端必须 fallback 显示 `avgTaskLatencyMs`，否则空数据期会显示 `null ms`。

### 11.3 Workflow reload 必须重拉

`POST /api/admin/workflow/reload` 只返回 `"reloaded"` 字符串。前端必须在 reload 完成后再调一次 `/active` 和 `/history` 才能刷新 UI。

### 11.4 多租户

- 所有 Admin/Report 接口都受 `SecurityUtils.currentTenantId()` 隔离。
- 跨租户访问返回 `NOT_FOUND`（不泄露资源存在性，不是 `FORBIDDEN`）。
- `workflow_node_run` 等下游表通过 `task_id` 子查询反查 `report_task.tenant_id`，**不冗余 `tenant_id` 列**。

### 11.5 RocketMQ topic 命名

- 必须用 **kebab-case**（`irp-task-created`），不能有大写或下划线，否则 broker 拒绝。
- 5 个 topic 全部在 `application.yml` 集中定义。

### 11.6 并发坑（历史已修）

- `HashMap.computeIfAbsent` 在并发 Consumer 下抛 CME → 改用 `ConcurrentHashMap`（`WorkflowLoader.cache`）。
- `ChatClient.Builder` 不是线程安全 → 改为每次调用 `.build()` 或预 build 单例。
- SnakeYAML 不自动 snake→camel → YAML 字段名直接写 camelCase。

## 14. 下一阶段（v1.1.0）候选方向

按价值 × 工作量排序，推荐**前 3 个**作为 v1.1.0 主轴（任选 1-2 个）：

### 🌟 推荐 A：可观测增强 → Per-Task 详情页

**为什么**：Admin Stats 看板有聚合数据，但单个任务的 Trace 详情页前端没做（仅有 `/report/{id}/trace` API）。补一个 **"任务详情 trace 可视化"** 页面，把 5 个节点的 input/output/tokens/latency/prompt_version 串成时间轴。

**价值**：面试场景拿出来"我能看每个 LLM 调用的输入输出 + 耗时 + 成本"，比单纯聚合数据有冲击力。

**工作量**：~6-8h（仅前端，后端 API 已有）。

### 🌟 推荐 B：Per-Tenant 语料库隔离

**为什么**：当前 `knowledge_doc` 全局共享，多租户场景下不合规。给 `knowledge_doc` 加 `tenant_id` 列 + `HybridRetriever` 加 filter + UI 给租户管理员一个"我的语料库"页。

**价值**：把多租户故事讲完整。Token 成本 / Trace / Judge 都已经按租户隔离了，只剩语料库这一环。

**工作量**：~10h（后端 DDL + 改造，前端加一个管理页）。

### 🌟 推荐 C：真训 LoRA Query Rewriter

**为什么**：`finetune/` 子模块骨架完整，只缺一次 30-60 分钟的训练。训完产出权重 + ROUGE-L / BLEU 评估数字。

**价值**：简历上"基于 Qwen2.5-1.5B + LoRA 微调"从骨架变成真实交付。

**工作量**：训练 1h + 部署 vLLM 1h + Java 侧 base-url 切换验证 1h = ~3h（如果机器现成）。

### 其它候选

| 方向 | 工作量 | 备注 |
|---|---|---|
| OpenTelemetry 替换自研 Trace | ~12h | 对接 Jaeger 演示；需要重写 Recorder |
| 引入超管角色 + 平台总览跨租户视图 | ~8h | 加一个 `ROLE_PLATFORM_ADMIN` 跳过 tenant 过滤 |
| 工作流可视化编辑器 | ~20h | UI 重头戏，但偏离核心 |

| WebSocket 替换 SSE | ~6h | 价值不大，SSE 对单向流足够 |
